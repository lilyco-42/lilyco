一个 struct，四端可用。

在结构体上挂一个 #[derive(App)]，框架就派生出 CLI、TUI、Web 与 MCP 四个入口。 参数、校验、进度、结果都从同一份 schema 来；连界面组件也只是后端的声明， 换 shadcn/ui 或其他 UI，业务代码一行不改。

CLI TUI Web MCP 52 类视图组件 Windows / Linux / Android
从第 1 章开始 看组件协议 源码

写一次，四个入口

// 一个命令 = 一个 struct
#[derive(App)]
#[app(name = "count", about = "统计文件", run = "run_count")]
struct Count {
    /// 要统计的文件
    #[arg(must_exist = true)]
    file: PathBuf,

    /// 最多显示多少行
    #[arg(default = 10, range = 0..=1000000)]
    limit: u32,
}

fn main() {
    lilyco::run::<Count>();   // ← 全部入口就在这一行
}

三分钟跑起来

建 crate

只依赖 facade，Web/TUI 用特性开关；默认构建是可移植的 CLI + MCP。

cargo new filecount && cd filecount
# Cargo.toml
lilyco = { version = "0.3", features = ["tui", "web"] }
serde_json = "1"

写一个命令

字段即参数：PathBuf 带校验、枚举变下拉、bool 变开关。

#[derive(App)]
#[app(name = "count", run = "run_count")]
struct Count { #[arg(must_exist = true)] file: PathBuf }

fn run_count(app: &Count, ctx: &Context) -> Result<Value, AppError> {
    ctx.done(serde_json::json!({ "file": app.file.display().to_string() }), 0);
    Ok(...)
}

挑一个入口

终端里自动进表单，管道里自动落 CLI；脚本与 agent 各有自己的口。

cargo run -- --file README.md              # CLI
cargo run -- --file README.md --json-stream
cargo run -- --gui                        # http://127.0.0.1:8080
cargo run -- --mcp                        # stdio server

为什么是这套形状

同一份契约

参数、必填、区间、安全等级只在 Rust 侧写一次；CLI 帮助、Web 表单、MCP inputSchema 都从它派生。

零外部依赖

内置 Web 端是内嵌单页：没有 CDN、没有 webfont、没有图标库，CSP 默认 default-src 'none'。

前端可替换

视图组件是带 kind 的 JSON；内置 GUI 只是其中一种实现，React + shadcn 是另一种。

人来确认，agent 不越权

MCP 面走 DenyElevated：T1+ 命令能被发现，但执行要人点头。

可验收

颜色进表、资源预算、装配顺序、无障碍结构都有测试盯着；设计文档与代码同仓。

全平台

默认特性就是 headless 的 CLI + MCP；Android / Termux 去掉 crossterm 即可编译。
